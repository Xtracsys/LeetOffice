# Debug Log — 2026-10-29

Session: full test run reported 2 failures; investigation uncovered a test
that had been writing into the **operator's real store**, a config data
race, and a self-deadlocking log filter. All root-caused and fixed in this
session. End state: 14/14 packages pass, `-race -count=2` clean on the
concurrency-touched packages.

## Bug 1 — `TestStartAtPathFailsClosedForLANBeforeOpeningStore` failed (deterministic)

**Symptom:** `StartAtPath error = <nil>, want fail-closed LAN mode error`.

**Root cause:** the in-flight LAN-hardening feature (see REQUIREMENTS
D20–D24) was half-landed: `config.Validate` rejected unsafe binds, but the
daemon never implemented the second gate the new test demanded — refuse to
start when `lan.enabled=true`, *before opening the store*.

**Fix:** `daemon.StartAtPath` checks `cfg.LAN.Enabled` immediately after
`config.Load` and returns
`LAN mode is not available in this build: keep listen.http on a loopback
address …`. The store is never opened for such a config (the test asserts
`storeDir` is not created).

## Bug 2 — `TestInviteRegenLiveEnroll` failed TempDir cleanup (flaky, parallel runs)

**Symptom:** `TempDir RemoveAll cleanup: … directory not empty`, preceded
by `digest: rename …: no such file or directory`.

**Root cause:** `StartLoops` spawns the jobs goroutine, which writes the
daily digest (a git commit) **immediately** at startup. The test ended via
`defer cancel()` — which only *signals* — so the goroutine could still be
mid-commit while `t.TempDir` cleanup ran. Lost the race only under full
suite parallelism (passed every time in isolation).

**Fix (three parts):**
1. `Node.loopsWG` tracks the loops started by `StartLoops`; new
   `Node.WaitLoops()` drains them (plus one pass over `syncRun` to catch a
   kicked sync, since `KickSync` stays fire-and-forget).
2. Loop-owning tests (`TestInviteRegenLiveEnroll`,
   `TestSyncEverySecRestartsTicker`, `TestFirstDigestDoesNotWaitUntilTomorrow`)
   now use `t.Cleanup(func(){ cancel(); n.WaitLoops() })` — and the two
   ticker/digest tests call `StartLoops` instead of hand-spawning
   goroutines so they are tracked.
3. `Daemon` got ownership of its loop context: `becomeNode` derives a
   cancellable ctx, and `Daemon.stopNode()` cancels + drains. The process
   shutdown path in `ListenAndServe` calls it too, so no loop outlives the
   HTTP server. Wizard tests call it in `t.Cleanup`.

## Bug 3 — the wizard test was operating on the REAL home store (data-integrity incident)

**Symptom (from the same full-suite log):**
`net: git service on [::]:7666 (mTLS, bare root /Users/config)` — a test
binding the *default* coordinator ports with the *home directory* as the
bare root.

**Root cause:** `TestSetupWizardFlow` POSTed `/setup/start` and
`/setup/local` without a `store_dir`, so `setupAction` fell back to
`config.DefaultStoreDir()` = `~/LeetOffice` — the operator's actual store.
Consequences on this machine (timestamps matched test runs exactly):
- created `~/main.git` (bare share) and `~/.leetoffice-identity/ca/`
  (a fresh team CA) — both never existed before that day;
- opened the real store, committed four `digest: 2026-10-29` entries
  attributed to the test actors `human:josh` / `human:maya`;
- **replaced the store's `origin` git remote** (`AddRemote` deletes and
  recreates) — from the real `leet://192.168.1.98:7666/main.git` to the
  test-created `file:///Users/config/main.git`.

**Remediation performed:**
- Test fixed: both wizard POSTs pass an explicit `store_dir` inside the
  test's temp dir (with a comment explaining why the default must never be
  used).
- `~/main.git` and `~/.leetoffice-identity/{ca,issued}` deleted (verified
  birth-times = test-run time, no leetd process running).
- Real store's `origin` remote restored to
  `leet://192.168.1.98:7666/main.git` from the untouched node.json.
- The four test digest commits were **left in the real store's git
  history** (audit trails are append-only; rewriting user history would be
  worse than the noise). They are identifiable by author
  (`human:josh`/`human:maya`) and timestamp (2026-10-29 19:07/19:09 UTC).

**Lesson (now in the test):** any test that drives the wizard without an
explicit `store_dir` mutates whatever store `DefaultStoreDir()` points at.

## Bug 4 — config data race: settings handlers vs background loops (pre-existing)

**Symptom:** `go test -race` flagged
`httpui.(*UI).saveSettings` writing `Config.Actor` /
`Config.SyncEverySec` while `daemon.(*Node).writeDailyDigest` read
`n.Cfg.Actor`.

**Root cause:** `*config.Config` is shared between HTTP handlers (settings
writes, invite regen, hide/unhide, MCP `mark_read`) and background loops
(sync ticker, digest, hygiene), but had no synchronization; handlers wrote
exported fields directly.

**Fix:** `config.Config` gained an internal `sync.RWMutex` with accessors
(`GetActor/SetActor`, `GetSyncEverySec/SetSyncEverySec`, `GetOllama/
SetOllama`, `Get/SetEnrollmentSecret`, `HiddenList`) and locking inside
`IsHidden/HideActor/UnhideActor/Subscribe/Subscription/MarkRead`. All
handler writes and all loop/handler reads go through them;
`Config.Save` snapshots under the lock. `go vet`'s copylocks check caught
one by-value Config copy in a test, now fixed. (Startup-only fields —
identity, paths, listeners, role — stay plain fields; they are written
before the config goes live.)

## Bug 5 — the log filter could deadlock itself (pre-existing, timing-exposed)

**Symptom:** under `-race -count=2`, `TestSetupWizardFlow` hung for the
full 10-minute timeout. Dump showed two goroutines blocked on the standard
logger's mutex:
- a coordinator startup `log.Printf` (waiting),
- `noiseFilter.Write` → `quietOnce.Do(log.Print)` (holding).

**Root cause:** `log.Logger.output` holds its mutex while calling its
writer. `quietKnownNoise` had installed `noiseFilter` as that writer — and
the filter's one-time notice called `log.Print`, re-entering the same
mutex. First benign mDNS line through the filter = permanent deadlock of
every goroutine that logs. Timing-dependent: the benign mdns line usually
arrived via mdns's own prefixed logger (bypassing the filter), which is
why normal runs survived.

**Fix:** the notice is written **directly to the underlying writer**
(`fmt.Fprint(n.w, …)`), never through the log package. While there, the
coordinator's git listener now closes on loop-ctx cancel (it previously
leaked the port across repeated in-process node starts, which is what made
`-count=2` resolve a second `[::]:7666` bind at all).
