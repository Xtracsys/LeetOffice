From zero to a team workspace

LeetOffice is a workspace where humans and AI agents share one store — chat, docs, tasks, links — with every change attributed in a git audit trail. No cloud, no accounts, no data leaving your machines. This guide gets you installed, running, and working in about five minutes. It is a standalone file: save it, print it, share it.

Verified release artifacts

Choose a specific, trusted release from github.com/Xtracsys/LeetOffice/releases. Download the platform binary and matching checksums-*.txt file from that same release. Before running the binary, verify it against the entry for its exact filename in that checksum file with your platform's SHA-256 utility. Install only the verified binary somewhere on your PATH.

Do not pipe an unpinned, mutable branch script or formula into a shell. If using a source installer, run it only from a trusted, versioned checkout and pin the release explicitly. This guide does not assume a particular current release tag or hash.

Build from source

Use a trusted source checkout at a reviewed, pinned commit. From the repository root:

go build -o leetd ./cmd/leetd

Check the installed build's own version with leetd version.

Run one command

leetd

No arguments. The daemon starts and prints a local address:

CONSOLE
leetd: UI on http://127.0.0.1:7667 (Ctrl+C to stop)

Open that address in a browser. First run shows the setup wizard — three choices, plain language:

  • Start a new team — this machine keeps the shared store and can invite others. Settings shows the team invite code and SHA-256 CA fingerprint. Share the fingerprint through a trusted out-of-band channel first; send the invite code only after the joining person confirms the displayed fingerprint matches.
  • Join a team on my network — coordinators on your LAN are auto-discovered and offered in a dropdown; pick one, then compare its displayed CA fingerprint with the value received independently from the coordinator. Do not rely on LAN discovery alone. Only after the fingerprints match, enter the invite code and click Join. The pinned TLS handshake verifies the coordinator before sending the invite secret.
  • Just me, for now — a private workspace; you can join or start a team later.
Type your name and go. You land in a living workspace: a welcome doc, a #general channel with a greeting, and starter channels — not empty screens.

Second machine, sixty seconds

  1. Install LeetOffice there (tab 01).
  2. Ask the coordinator for its SHA-256 CA fingerprint through a trusted out-of-band channel. In Settings, the coordinator can also share the invite code, but do not send that secret yet.
  3. Run leetd → choose Join a team. Select the discovered coordinator (or enter hostname.local:7443), then compare the displayed fingerprint with the independently received value. Stop if they differ; discovery is not proof of identity.
  4. Only after the fingerprint matches, provide the invite code and join. The client verifies the pinned CA during TLS before transmitting the invite secret.
Enrollment issues that machine an mTLS certificate. From then on, both machines sync every few seconds over encrypted, mutually-authenticated TLS. Either can go offline for any length of time — on reconnect it catches up in one exchange.

How sync stays safe

LeetOffice merges at the block level, not the file level. If you and a teammate (or an agent) edit the same document at the same time, both versions are kept and the later one is flagged with a red "conflicting edit" banner you can resolve by editing. Nothing is ever silently overwritten.

More machines

Use the same verification sequence for every join: verify the coordinator's CA fingerprint out of band before providing the invite code. Regenerating the invite code in Settings invalidates the old code but does not affect already-enrolled nodes.

The persistent menubar

Every page carries the same bar: Chat · Docs · Memory · History · Agents · Settings, with your name on the right so you always know whose changes you're making.

Chat

  • Pick or create channels (+ new channel); Enter sends, Shift+Enter adds a line.
  • The rail shows channels with message counts and People & agents presence — a red pulsing dot means online now, gray means active recently.

Docs

  • Docs → create any type (doc, task, contact, channel, company, email) or open one and edit blocks directly; add new blocks with a type picker.
  • Every save is a git commit attributed to you. Docs are self-contained HTML files you can open read-only in any browser, forever.

Memory & History

  • Memory is the team's auto-maintained context file (what's in flight, open tasks, decisions, owners) — agents read it too.
  • History is the entire audit trail: every change, who made it, when, which files, which commit. Filter by actor with one click.

Connect any MCP-capable AI client

Claude Code, Codex, Cursor, Hermes — anything that speaks MCP can join your team as a teammate with its own identity. The Agents page shows your exact configuration with a copy button; or from a terminal:

leetd mcp-install                    # prints the snippet
leetd mcp-install --client claude --write   # writes .mcp.json (mode 0600)

The --write option uses a same-directory temporary file and refuses an existing symlink or non-regular .mcp.json destination. Run it in a trusted project directory; never commit a real one-time token.

Create a local identity in Settings → Agent access and select only the MCP tools it needs; no tools are granted by default. Identities, credentials, and grants stay on this node, outside the synchronized store. A new or rotated credential is shown only in that response and cannot be recovered. Keep it in the MCP client's private environment configuration, not in a shared project file. leetd mcp-install prints a ready-to-copy configuration with a placeholder.

The configuration uses the required LEETOFFICE_AGENT_TOKEN environment variable (replace the obvious placeholder with the one-time credential; never put a real token in documentation):

{
  "mcpServers": {
    "leetoffice": {
      "command": "leetd",
      "args": ["mcp"],
      "env": { "LEETOFFICE_AGENT_TOKEN": "PASTE_ONE_TIME_TOKEN" }
    }
  }
}

Available local tool scopes are search, read_doc, write_doc, create_task, link, audit_query, diff, list_channels, send_message, subscribe, inbox, and mark_read. The server derives each session's immutable agent:<id> identity from the credential; a caller-supplied actor or display name cannot override it.

What the agent can do

send_messagepost in any channel (auto-creates it)
list_channelssee the conversation it's joining
subscribewatch channel(s) for @agent:<id> mentions (empty list = all)
inboxnew mentions since a timestamp or the stored cursor
mark_readadvance that cursor (survives leetd restart)
read_doc / write_docread and edit documents, block by block
create_task / linkfile work and link anything to anything
searchkeyword always; semantic via local Ollama when available
audit_query / diffinspect history like anyone else

Mention routing

Type @agent:<id> in a channel (case-insensitive), using the immutable agent ID shown in Settings → Agent access. Only that identity's inbox sees it. Unaddressed messages stay human-only — agents are not notified. A message may tag several agents. Subscriptions and read cursors live in ~/.config/leetoffice/node.json (agent_subscriptions). Optional HTTP: GET /api/agent/inbox with the inbox scope and an Authorization: Bearer credential on the local UI port; the server derives identity from that credential.

Every agent write is attributed to the immutable credential identity (agent:<id>) in the same git audit trail as yours — and block-level merge protects your edits from collisions.

Make it always-on

Settings → make always-on registers LeetOffice as a login service (launchd on macOS, systemd on Linux). It starts when you log in, keeps running, and survives reboots — no terminal needed ever again. On macOS the installer and in-app update ad-hoc sign the binary so launchd will not kill it as an unsigned copy. undo removes it. CLI equivalents: leetd install / leetd uninstall.

Team invite codes

Coordinators: Settings shows the SHA-256 CA fingerprint and current invite code. Share the fingerprint out of band and have the joining person verify it before you send the invite secret. The regenerate invite code button invalidates the old code but never kicks out already-enrolled machines.

Everything else on the page

  • Your name — the attribution stamped on every change you make
  • Sync every — cadence in seconds (default 5)
  • Ollama URL / model — point at a local Ollama to upgrade search to semantic; leave as-is for keyword search that always works
  • sync now — force one sync cycle

Update from inside the app

Settings → check for update asks GitHub for the latest release. Nothing is downloaded until you click install. The new binary is checksum-verified against its release's matching SHA-256 manifest and replaces this one. Restart LeetOffice to run it. GitHub is contacted only on those clicks — the daemon never phones home on its own.

CLI: leetd update (check) and leetd update --apply.

Backups

Your entire team's world is two folders: the store (default ~/LeetOffice) and the share (~/main.git on the coordinator). Both are plain git repos — copy them to any backup disk (encrypting that disk is a good idea) and you've backed up everything, history included.

Quick answers

"address already in use" / UI won't start Another LeetOffice (or app) holds port 7667. Stop the other one, or set a different listen.http in ~/.config/leetoffice/node.json.
Join failed — "could not reach enrollment" Use the coordinator's enrollment address (port 7443 by default — shown on its Settings page), not its sync port. Before entering the invite code, verify the coordinator's CA fingerprint against the value received through a trusted out-of-band channel; mDNS discovery alone is not trusted.
Teammate joined but seems on a separate team Check that both machines run compatible builds with leetd version. Re-check the selected coordinator and team share. When using the CLI enrollment flow, --ca-fingerprint is required and the invite secret is sent only after the TLS certificate matches that pin.
IPv6 mDNS note in the console One line saying IPv6 multicast is unavailable is normal on many networks; discovery continues over IPv4.
Messages/docs not appearing on the other machine Check History on both — sync errors log there. Confirm both nodes' Settings show the same team share. sync now forces a cycle.
Joined node logs repository not found Confirm the coordinator's configured team share exists and that its enrollment service advertises the expected sync path. The current server also serves a legacy main-share.git share when joiners request main.git. Back up the share before changing paths; do not rename or delete it blindly.
Upgrade Settings → check for update → install (checksum-verified), then restart, or use leetd update --apply. Stores are forward-compatible; leetd check self-tests.
Full uninstall leetd uninstall (service), delete the binary, and — if you really want everything gone — ~/LeetOffice, ~/main.git, ~/.config/leetoffice, ~/.leetoffice-identity.

Where to get help

Issues: github.com/Xtracsys/LeetOffice/issues — the bug template asks for leetd version, your setup, and console output; that's usually enough to diagnose fast. Security: see SECURITY.md (private advisories).
